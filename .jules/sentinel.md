## 2024-05-08 - Added Request Size Limits to Prevent Denial of Service
**Vulnerability:** The CLI fetched remote URLs directly into memory without any size constraints. A malicious or misconfigured server returning a multi-gigabyte HTML response would cause an Out of Memory (OOM) error, creating a Denial of Service (DoS) vulnerability.
**Learning:** Even simple CLI fetch tools are susceptible to resource exhaustion attacks if response sizes are unbounded, especially since `requests.get` without `stream=True` buffers the entire response in memory.
**Prevention:** Always use `stream=True` when downloading untrusted resources, and enforce a strict upper limit on downloaded bytes.
## 2026-07-18 - Prevent Server-Side Request Forgery (SSRF) in CLI URL Fetcher
**Vulnerability:** The CLI fetched remote URLs directly into memory based on user input, which opened up a critical SSRF vulnerability where an attacker could access internal, private, or loopback IPs (e.g. `127.0.0.1`, `169.254.169.254`) on the server. Furthermore, the `requests` library automatically follows HTTP redirects, which an attacker could use to bypass simple IP blocklist checks by initially pointing to a public IP that subsequently redirects to an internal one.
**Learning:** Using `socket.getaddrinfo` allows for consistent resolution of both IPv4 and IPv6 addresses. We must also explicitly check for `ip_obj.is_unspecified` alongside `is_private` and `is_loopback`, as `0.0.0.0` resolves to localhost on Linux and can be used to bypass SSRF filters. Additionally, to properly mitigate SSRF in URL fetchers, HTTP redirects must be disabled (`allow_redirects=False`) and handled manually so that the target `Location` can be vetted before each jump.
**Prevention:** Always validate resolved IPs for loopback, private, and unspecified addresses before initiating requests. Disable automatic redirects when fetching untrusted URLs and evaluate redirect destinations manually to prevent bypasses.
