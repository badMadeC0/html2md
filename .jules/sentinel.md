## 2024-05-08 - Added Request Size Limits to Prevent Denial of Service
**Vulnerability:** The CLI fetched remote URLs directly into memory without any size constraints. A malicious or misconfigured server returning a multi-gigabyte HTML response would cause an Out of Memory (OOM) error, creating a Denial of Service (DoS) vulnerability.
**Learning:** Even simple CLI fetch tools are susceptible to resource exhaustion attacks if response sizes are unbounded, especially since `requests.get` without `stream=True` buffers the entire response in memory.
**Prevention:** Always use `stream=True` when downloading untrusted resources, and enforce a strict upper limit on downloaded bytes.

## 2024-06-25 - Prevented SSRF in URL Fetcher
**Vulnerability:** The CLI fetched external URLs directly using `requests` without restricting internal, loopback, or private IPs. Because `requests` follows redirects natively, this would allow an attacker to bypass basic input validations using a service like `httpbin.org/redirect-to?url=...` and force the application to fetch sensitive internal endpoints (like `169.254.169.254` for AWS metadata or `localhost` services).
**Learning:** URL validation based purely on the string format or protocol scheme (e.g., checking for `http`/`https`) is insufficient because DNS resolution and HTTP redirects can point those seemingly valid URLs to protected internal network segments.
**Prevention:** Mount a custom `requests.adapters.HTTPAdapter` to the `requests.Session` that intercepts every request right before dispatch, extracts the target hostname, performs DNS resolution (`socket.gethostbyname`), and verifies the resulting IP using `ipaddress` (`is_private`, `is_loopback`, `is_link_local`) before continuing. This mechanism applies even across redirects natively handled by `requests`.

## 2024-06-25 - Prevented SSRF IPv6 & 0.0.0.0 Bypasses
**Vulnerability:** Initial SSRF protection used `socket.gethostbyname` which only resolves IPv4 addresses and fails on IPv6 domains. Catching the failure and allowing the request to proceed (fail-open) allowed bypasses via IPv6 (e.g., `http://[::1]/`). Furthermore, relying solely on `is_private`, `is_loopback`, and `is_link_local` missed the "unspecified" address (`0.0.0.0`), which resolves to loopback on Unix systems, leading to another bypass.
**Learning:** Security controls must fail securely (fail-closed). If an address cannot be validated, it must be denied. Furthermore, IP validation must account for all IP families (IPv4 and IPv6) and special IP types like `0.0.0.0` (`is_unspecified`).
**Prevention:** Used `socket.getaddrinfo` instead of `socket.gethostbyname` to obtain all IP addresses (IPv4 and IPv6) for a given hostname. Included a check for `ipaddress.ip_address(ip).is_unspecified` to block `0.0.0.0` SSRF attempts. If resolution fails (`socket.gaierror`), the request is actively blocked by raising a `ConnectionError` instead of falling through.
